# Security and Safety Policy

This document details the security practices, session isolation policies, input validation rules, and safety guardrails implemented in the PulseOS Clinical Decision Support platform.

---

## 1. Data and Session Isolation

### In-Memory Session Partitioning
PulseOS does not utilize a persistent shared database for storing user records. Instead, it manages state using the Google Agent Development Kit (ADK) `InMemorySessionService`.
* Clinical session details and the Patient Digital Twin structure are partitioned using a unique `session_id` query parameter generated by the client application.
* Session namespaces are isolated at the server level in the nested map structure:
  ```python
  session_service.sessions["app"]["patient_user"][session_id]
  ```
  This ensures that Patient A cannot query, overwrite, or access clinical records associated with Patient B.

### Data Minimization and Privacy
* The application processes clinical indicators without requiring Personally Identifiable Information (PII) such as full names, social security numbers, or exact dates of birth.
* Identifiers are anonymized using simulated keys (e.g., `PT-9942`) to limit exposure in transit and in logs.

---

## 2. Clinical Safety Guardrails

### Educational Framing (Non-Diagnostic)
* PulseOS is a Care Coordination and Health Navigation tool, not a diagnostic engine.
* LLM coordinator and specialist agents (defined in the agent definitions) are programmed with explicit system instructions to frame all guidance as educational reference materials.
* The system is restricted from issuing definitive clinical diagnoses or prescribing therapeutic plans.

### Automatic Disclaimers
* Agent response templates and interactive tools default to recommending professional consults with primary care providers, pharmacists, or specialists when critical indicators are detected.

---

## 3. API Resilience & Availability

### Network Request Timeouts
* All outbound calls to third-party endpoints (specifically the National Library of Medicine RxNorm and NCBI E-Utilities APIs) enforce strict timeouts (4–5 seconds) to prevent server threads from hanging indefinitely and protect the platform against Denial of Service (DoS) blockages.

### Local Fallback Databases
* To guarantee application availability during network disruptions, PulseOS maintains local offline dictionaries of critical drug-drug interactions and standard lab threshold references. If an external API query fails, the system falls back to these internal records automatically.

### Key Management
* PulseOS does not store or hardcode private keys for public NIH RxNorm or NCBI PubMed API requests, as these endpoints do not require authorization for standard queries, eliminating credential exposure vectors.

---

## 4. Input Validation & Schema Protection

### Pydantic Verification
* All data entry points are validated at the FastAPI server boundary using Pydantic models.
* Strict typing and schema boundaries are enforced on models such as `PatientDigitalTwin`, `HealthRecord`, `LabResult`, and `LabInput`. Malformed payloads, unauthorized attributes, or injection formats are rejected at the REST API handler before processing.
